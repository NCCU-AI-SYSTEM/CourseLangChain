# 離線檢索評估

回答一個問題：**RRF 融合真的比單用 BM25 或單用向量好嗎？好多少？**

README 裡「BM25 擅長專有名詞、向量擅長語意」的說法來自失敗案例的對照。
這裡把它變成可重現的數字：同一組查詢、三種檢索方式、帶信賴區間的差異。

評估直接重用 `tools/retrieve.py` 的 SQL 與參數，量到的就是正式系統在跑的那段檢索。

## 查詢集：四層、兩種標註方式

| 題型 | 例子 | 題數 | 怎麼標註 |
|---|---|---|---|
| 教師姓名 | 王小明老師開的課 | 30 | **規則**：那位老師開的每一門課都相關 |
| 精確課名 | 統計學 | 30 | **規則**：同名的每一門課都相關 |
| 主題 | 機器學習 | 20 | **人工** |
| 口語長句 | 想學統計但數學不太好 | 20 | **人工** |

前兩層從資料庫隨機抽樣（固定種子），相關性由規則完全決定，不需要人看。
為了讓題目之間可比，只抽相關課程不超過 8 門的老師與課名。

後兩層的題目寫在 `queries_manual.tsv`，可以直接改。相關性要人工判斷，評分標準：

| grade | 意思 | 例子（查「機器學習」） |
|---|---|---|
| 2 | 直接符合需求 | 機器學習、深度學習導論 |
| 1 | 部分相關 | 資料探勘、統計學習 |
| 0 | 不相關 | 微積分 |

標註池用 TREC 的匯集法：每個系統取前 10 名，聯集起來給人標。
候選順序打亂、不標來源，標註的人看不出是哪一路找到、排第幾。

## 怎麼跑

```sh
cd ~/NCCU_AI_Project/CourseLangChain
docker compose up -d postgres                     # Docker Desktop 要先開

uv run python -m evaluation.build_gold sample     # 1. 抽規則層、合併人工題目
uv run python -m evaluation.build_gold pool       # 2. 匯出人工層的待標註候選
# 3. 編輯 evaluation/judgments.tsv，把 grade 欄填上 0、1、2
uv run python -m evaluation.run_eval              # 4. 產生 evaluation/results/report.md
```

**不用等全部標完。** 規則層在第 1 步之後就能評估；人工層哪一題標完，哪一題就會被納入。
報告會列出每層納入幾題、幾題還沒標完。

**標註表不要用 Excel 直接開再存檔。** 13 碼課號會被轉成科學記號而壞掉。
用 VS Code 編輯最安全；真的要用 Excel，匯入時把 `course_id` 欄設成「文字」。
壞掉的課號會讓程式直接報錯，不會默默算進分數。

第一次跑會載入 embedding 模型，沒有快取時要下載約 400MB。

## 指標與統計

- **Recall@10**：相關課程有多少比例出現在前 10 名。
- **MRR@10**：第一門相關課程名次的倒數，看使用者多快看到對的課。
- **nDCG@10**：分級版本，直接符合排在前面比部分相關排在前面得分高。
- **judged@10**：前 10 名中已標註的比例。未標註一律算不相關，低於 0.9 表示分數被低估，要重跑 pool。

系統間的差異用**分層成對 bootstrap** 估 95% 信賴區間。
成對，是因為同一組題目比較兩個系統，逐題相減可以抵銷題目本身的難易。
分層，是因為查詢集本來就按題型建立，各層分開重抽才不會讓題型比例的變異混進區間。

另外會掃 RRF 的 k = 10、30、60、100，看正式設定的 60 是否站得住。

## 已知限制

- 人工層的題目是開發者擬的，不是真實使用者的提問紀錄。
- 規則層的標註很嚴格：查「統計學」時，「生物統計學」算不相關。
- 標註只有一個人，沒有標註者間一致性。
- 只評估單一學期的資料，評估的是檢索本身，不含 Agent 選工具與時間條件過濾。

測試：`uv run python -m tests.test_eval_metrics`（不需要資料庫）。
